## 1. 项目概述

### 1.1 产品定位

本项目是一个“AI 驱动的多人在线文本博弈系统”。玩家在同一房间进行回合制决策，AI 根据规则、背景、事件与玩家动作进行推演，输出叙事结果和状态变化，并进入下一回合。

### 1.2 核心价值

- 为玩家提供“可重复开局、不可重复过程”的策略叙事体验。
- 通过主持人配置与审阅机制，实现“可控的 AI 生成”。
- 通过自动恢复机制降低 AI 调用失败、超时、状态不一致导致的中断风险。
- 提供交易、任务、策略分析、历史复盘、存档恢复等扩展玩法。

### 1.3 主要角色

- 玩家：加入房间、提交回合决策、查看推演结果、执行交易/任务。
- 主持人（Host）：配置 AI 接口与规则、开启游戏、审阅决策、提交 AI 推演、异常恢复。
- 开发管理员：用户治理、房间治理、系统维护（`/api/admin/*`）。

### 1.4 业务边界

- 已覆盖：账号认证、房间生命周期、回合制博弈主流程、实时同步、AI 推演、恢复与存档、辅助系统。
- 不在当前主闭环：Forgot/Reset 密码完整链路（前端遗留页面存在，但后端接口已移除）。

## 3. 产品经理视角

### 3.1 核心用户场景与旅程

| 阶段 | 用户动作 | 关键页面 | 关键接口/事件 | 输出结果 |
| --- | --- | --- | --- | --- |
| 账号阶段 | 注册/登录 | `Login.tsx` `Register.tsx` | `/api/auth/register` `/api/auth/login` | 获得 token 与用户身份 |
| 组局阶段 | 创建/加入房间 | `Rooms.tsx` `WaitingRoom.tsx` | `/api/rooms/create` `/api/rooms/:roomId/join` `join_room` | 房间可进入“主持人配置” |

| 开局阶段 | 生成初始化并开局 | `HostReview.tsx` | `/api/game/:roomId/generate-init` `/api/game/:roomId/start` | 形成首回合状态 |
| 决策阶段 | 玩家提交回合动作 | `GameSession.tsx` | `/api/game/:sessionId/decision` | 决策集合可审阅 |
| 审阅阶段 | 主持审阅并提交 AI | `HostReview.tsx` | `/api/game/:sessionId/start-review` `/submit-to-ai` | 进入 AI 推演 |

| 续局阶段 | 下一回合 / 结束 | `GameSession.tsx` | `/api/game/:sessionId/round/:round/next` | 新一轮或游戏完成 |

### 3.2 功能矩阵（面向产品能力）

| 能力域 | 功能点 | 业务价值 |

| 房间与组队 | 创建/加入/离开/关闭房间，主持人与玩家角色分离 | 支撑多人协作与主持治理 |
| 核心博弈 | 决策、审阅、推演、结果、下一回合 | 构成核心游戏闭环 |
| 扩展玩法 | 交易、任务、策略分析 | 增强策略深度与复玩率 |

| 实时互动 | WebSocket 同步、断线重连、增量更新 | 提升多人在线体验连续性 |
| 主持控制 | 时限调整、恢复面板、快照 | 降低 AI 波动导致的中断风险 |

### 3.3 关键产品规则

- 回合状态机：`decision -> review -> inference -> result -> next`（直到 `finished`）。
- 主持人权限边界：主持人负责配置与审阅；玩家不能直接推进回合阶段。
- 决策时限机制：会话含 `decisionDeadline`，超时后流程按策略进入后续处理。
- 超时流转策略已落地：`auto_submit / auto_skip / bot_takeover`，并支持主持人手动触发 `POST /api/game/:sessionId/round/:round/apply-timeout-strategy`。
- 房间成员约束：大多数接口要求用户为房间在场成员（`status != left`）。
- 管理口限制：`/api/admin/*` 需开发管理员身份。

### 3.4 产品指标建议（可用于验收与迭代）

- 活跃与留存：DAU、次日留存、单局平均时长、单用户周局数。
- 对局质量：平均每局回合数、超时决策率、主持审阅修改率、AI 失败率。
- 稳定性：恢复操作触发率、恢复成功率、断线重连成功率、同步延迟。
- 玩法渗透：交易参与率、任务完成率、策略分析页访问率、存档使用率。
- 商业化前置（如未来需要）：高活跃用户占比、内容分享率、付费意愿调查。

### 3.5 验收口径（PM 视角）

- 主流程必须“从创建房间到至少完成 1 回合 AI 推演”可稳定跑通。
- 三人联机条件下，断线重连不应破坏会话状态一致性。
- 主持恢复面板必须可检测异常并提供可执行恢复操作。
- 历史与存档功能可用于最少一次“复盘 + 回滚 + 再继续”演示。

## 5. 算法视角

### 5.1 算法系统定位

算法核心是“可解释 Prompt + 多阶段状态约束 + 容错执行”：

- 不是自由对话 Agent，而是规则驱动推演器。
- 目标是稳定地产出结构化回合结果（叙事、事件、面板数据、下一回合提示）。

### 5.2 推演输入输出结构

1. 输入（`InferenceRequest`）
- 会话标识：`sessionId`、`round`
- 决策集合：玩家动作文本、可选结构化动作信息
- 上下文：`gameRules`、活动事件、初始化实体状态

2. 输出（`InferenceResult`）
- `status`: completed/failed
- `result`: narrative/outcomes/events/nextRoundHints 等
- `completedAt` 与错误信息

### 5.3 Prompt 架构设计（`PromptBuilder`）

推演 Prompt 按固定顺序拼接：

1. Core Rules（不可违背硬约束）
2. Scenario（场景背景与胜利条件）
3. Temporary Rules（临时修正规则 + 卦象）
4. Active Events（进行中的事件）
5. Entity States（主体资源状态）
6. Decisions（玩家动作输入）
7. Execution Instructions（输出格式和执行要求）

价值：
- 提高模型可控性与输出一致性。
- 便于后续规则扩展和 A/B 实验。

### 5.4 长短期记忆机制

1. 会话历史记忆（短中期）
- 表：`AIConversationHistory`
- 默认策略：保留最近 10 回合，估算 token 上限 16000，超限则压缩。

2. Lorebook（长期记忆）
- 按关键词触发注入，支持优先级、激活次数控制。
- 推演结束可反哺 Lorebook，形成持续演化的世界知识。

### 5.5 调用与容错策略（`aiService`）

- 重试：默认 5 次，退避等待。
- 超时：常规 120s，初始化任务更长。
- 响应解析：支持多 provider 结构与通用 JSON 回退解析。
- JSON 硬约束：支持 provider（OpenAI/Zhipu）可通过 `useJsonSchema` 开关注入 `response_format: { type: "json_schema" }`，降低结构化输出失败率。
- 降级：解析失败时返回可用默认结构，避免流程完全中断。

### 5.6 决策选项生成

- 通过 `generateDecisionOptions` 给玩家生成 3~4 个候选选项。
- 首回合优先使用初始化阶段生成的 `initialOptions`，减少首轮波动。

### 5.7 恢复算法（`GameRecoveryService`）

1. 异常检测
- `inference_timeout`
- `no_decisions`
- `missing_result`
- `data_inconsistency`

2. 恢复动作
- `retry_inference`
- `skip_round`
- `rollback_round`
- `force_next_round`
- `reset_to_decision`
- `fix_data_inconsistency`
- 以及快照创建能力

### 5.8 算法评估建议

- 结构化质量：可解析率、字段完整率、非法字段率。
- 叙事质量：连贯性评分、重复率、角色一致性。
- 博弈有效性：决策差异敏感度、事件推进合理性、回合节奏稳定性。
- 运行稳定性：超时率、重试成功率、恢复成功率。

## 6. 已知问题与技术债（当前代码已确认）

### 6.1 重复路由定义（高）

- 位置：`backend/src/routes/game.ts`（如 635/2881 的 `GET /history/:sessionId`，804/2991 的 `DELETE /history/:sessionId`）
- 影响：维护复杂度高，后续改动易产生行为不一致与覆盖风险。
- 建议：拆分历史路由子模块，保留唯一注册点，并补充路由冲突测试。

### 6.2 Redis Key 命名含多余空格（已修复，2026-03-03）

- 位置：`backend/src/routes/trade.ts:129,257,436`
- 原问题：`trade: expire:${id} `（含空格）
- 修复后：统一为 `trade:expire:${id}`，已避免过期任务删除失败。
- 后续建议：如线上已有历史脏 key，补一次性迁移/清理脚本。

### 6.3 清理脚本 Redis 变量未定义（高）

- 位置：`backend/scripts/cleanup-database.ts`（使用 `redis` 但未 import/实例化）
- 影响：`--redis` 或 `--all` 模式下脚本运行失败。
- 建议：补充 `import redis from '../src/utils/redis'`（或独立客户端）并增加脚本自测。

### 6.4 前后端认证能力不一致（中）

- 位置：
  - 前端：`frontend/src/services/auth.ts:45-46` 仍调用 `/auth/reset-password`
  - 后端：`backend/src/routes/auth.ts:180` 明确忘记/重置密码接口已移除
  - 前端路由：`frontend/src/App.tsx` 未挂载 `ForgotPassword/ResetPassword`
- 影响：功能口径混乱，遗留页面与服务调用可能误导开发与测试。
- 建议：要么恢复后端接口并重新挂路由，要么移除前端遗留实现。

### 6.5 源码注释/文案编码异常（中）

- 位置：后端与前端多个文件存在乱码注释（如 README、路由注释、组件文案）。
- 影响：可维护性和协作效率下降，增加误读风险。
- 建议：统一 UTF-8 编码并进行批量校正。

### 6.6 管理权限判断策略偏弱（中）

- 位置：`backend/src/routes/admin.ts`（按 `username` 判断管理员）
- 影响：权限模型缺乏角色字段约束，可扩展性与安全性不足。
- 建议：引入 `role` 字段 + 服务端强校验 + 审计日志。

### 6.7 Socket CORS 过宽（中）

- 位置：`backend/src/server.ts` Socket 配置 `origin: '*'`
- 影响：生产环境安全面扩大，可能引入跨站连接风险。
- 建议：区分开发/生产配置，生产仅允许白名单来源。
